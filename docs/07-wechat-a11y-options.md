# 07 · 微信控件树不可见：原因验证与方案对比

> 日期：2026-11-25　设备：Redmi 25102RKBEC / Android 16 / KernelSU
> 结论先行：**不是自研渲染器，是"已启用服务白名单"门控**；截图与手势一直可用，被隐藏的只是控件树。

## 1. 关键实验（可复现）

| 步骤 | 启用的无障碍服务 | 微信 `nodeCount` |
| --- | --- | --- |
| 基线 | 仅 `dev.everything.vision` | **1** |
| 共启 | 自研 + TalkBack | **376**（`从前的我`、`二帅`、`公众号`…） |
| 共启 | 自研 + Switch Access（静默） | **376**（同上） |
| 还原 | 仅自研 | **1** |

命令（root）：

```bash
# 共启静默服务
settings put secure enabled_accessibility_services \
  'dev.everything.vision/dev.everything.vision.A11yService:com.google.android.accessibility.switchaccess/com.android.switchaccess.SwitchAccessService'
# 还原
settings put secure enabled_accessibility_services \
  'dev.everything.vision/dev.everything.vision.A11yService'
```

**判读**：截图（`takeScreenshot`）与手势（`dispatchGesture`）在微信里从未失败；只有 `rootInActiveWindow` 返回 1 个 `FrameLayout`。
若真是自研渲染（SurfaceView/自绘），TalkBack 也不会让节点凭空出现——因此排除"渲染导致不可读"。

## 2. 机制推断

微信在检测到"非白名单无障碍服务在运行"时，对无障碍树做了裁剪（把内容标记为不可见/不导出）。
启用一个被系统认可的辅助服务后，微信恢复导出整棵树，**所有服务都能读到**（我们自己的服务读到了 376 个节点）。

这解释了为什么 GKD、我们的驱动都只看到 1 个节点——受害者不是某一个工具，而是"未被识别"。

## 3. 四种方案对比

| 维度 | ① 伪装白名单 | ② 共启静默系统服务（局部无障碍的现实形态） | ③ OCR + 视觉点击 | ④ 专用通道（Intent/IME） |
| --- | --- | --- | --- | --- |
| 技术路径 | LSPosed/Xposed 挂钩 `getEnabledAccessibilityServiceList`，或伪造服务信息 | 同时启用 Switch Access 等系统辅助服务 | 截图 → OCR/模板 → 坐标点击 | `SEND` + FileProvider、自定义输入法、通知回复、深链 |
| 实测可行性 | 未实现（需额外框架） | ✅ 已实测：1 → 376 节点 | 截图/手势已验证可用；OCR 未装 | 部分验证（SEND 因 URI 授权失败过一次） |
| 稳定性 | 低：微信/ROM 更新即失效 | 中：微信改检测逻辑可能失效，但机制简单 | 中：字体/主题/分辨率为变量 | 高（走公开接口） |
| 覆盖率 | 高（解禁后全树） | 高（解禁后全树，含按钮语义） | 低-中：只认"看到的"，无控件角色 | 低：只覆盖特定动作 |
| 性能 | 快（a11y） | 快（a11y） | 慢：单步 1–1.5s（抓帧+OCR+决策） | 快 |
| 开发成本 | 高（框架、适配、维护） | **低**（设置开关 + 能力探测） | 中（OCR 集成、版面理解） | 低-中（每场景单独做） |
| 用户影响 | 需装框架，风险外溢 | 多一个辅助服务常驻（可静默） | 无系统改动 | 无 |
| 合规/封号风险 | **高**：明确的对抗性绕过 | **中-高**：机制合法，但仍可能被判定为自动化 | 低-中：无对抗，但自动化本身仍受条款约束 | 低 |
| 可逆性 | 需卸载框架 | 一条命令，可逆（实测已还原） | 无侵入 | 无侵入 |

### 3.1 关于"伪装成白名单"

- 本质是让微信误以为系统里跑着它认可的服务，属于**对抗性绕过**；
- 需要 LSPosed 等框架，微信每次改动检测逻辑都要重新适配；
- 与账号风控直接冲突（微信对自动化/外挂的处罚包括限制登录、封号）；
- **不建议**做：收益（和共启静默服务一样）与风险严重不匹配——既然"真启用一个静默服务"就能达到同样效果，就没有理由去伪装。

### 3.2 关于"局部无障碍"

- 原意可能是"只在部分页面用无障碍"，但实测表明更有效的形态是：**共启一个静默的系统辅助服务**（Switch Access），让微信恢复导出；
- 优点：改动小、可逆、立刻拿到 376 个节点，按钮/输入框语义都在，自动化质量回到正常水平；
- 代价：多一个常驻服务；部分 ROM 可能有悬浮/扫描行为；微信若调整检测会失效；
- **仍需注意**：这依然绕过了微信"不希望被自动化"的设计意图，账号风险由使用者承担。

### 3.3 关于 OCR + 视觉点击

- 我们的截图和手势在微信里完全可用，这条链路**一定能跑通**；
- 但 OCR 解决"看见字"，解决不了"知道哪块能点"——按钮、开关、输入框都没有语义，只能靠模板/位置启发式；
- 单步成本：抓帧 400–600ms + OCR 300–800ms + 决策 ≈ **1–1.5s/步**，10 步任务就是 10–15s，且每步都可能错；
- 中文 OCR 需要装 tesseract/PaddleOCR（当前未装，体积 50–100MB）；
- 适合做**兜底**（没有树、或树不可信时），不适合当主路径。

### 3.4 关于专用通道（补充，常被忽略）

| 场景 | 通道 | 说明 |
| --- | --- | --- |
| 发送图片/文件 | `ACTION_SEND` + `FileProvider` | 用自己 App 的 content URI 并授权读，不需要相册权限 |
| 输入文字 | 自定义输入法（IME） | 可绕过 `ACTION_SET_TEXT` 的限制 |
| 回复消息 | 通知 `RemoteInput` | 仅限通知栏可见的消息 |
| 打开特定页面 | `weixin://` 深链 | 官方未承诺，稳定性一般 |

这些不是万能，但**没有对抗性**，适合做"确定性动作"的补充。

## 4. 推荐路线（分层）

| 层 | 做什么 | 触发条件 |
| --- | --- | --- |
| L0 诊断 | 抓帧后若 `nodeCount ≤ 2` 且不是白屏，判定"树被门控" | 每次任务开始 |
| L1 主路径 | a11y 选择器/坐标（现有能力） | 有树 |
| L2 兼容模式 | 提示用户一键共启静默辅助服务（Switch Access），可一键还原 | L0 判定门控 |
| L3 兜底 | 模板匹配（已有）+ OCR（v1.2） | 无树或兼容模式不可用 |
| L4 专用通道 | Intent/IME/通知回复 | 已知场景 |

**不做**：伪装白名单、Xposed 挂钩。

## 6. 风险声明

- 共启辅助服务虽属合法配置，但用于自动化微信仍可能违反其用户协议，存在账号风险；
- 本文只做技术验证与记录，不提供伪装/挂钩实现；
- 实验中临时启用的 TalkBack/Switch Access **已还原**，当前仅保留自研服务（`nodeCount=1` 已复验）。
