## 1. 背景与来源

用户最初的诉求是："把 `gkd-kit/inspect` 拉下来，看能不能基于它做一个**实时看见并操控屏幕**的方案"。
调研过程中目标逐步收敛为：

1. 能力要**实时**（能看见当前屏幕、能立即操作）；
2. 使用方（目标应用/服务）的**配置步骤尽量少**；
3. **产线不复用 GKD 应用**，但开发测试阶段可以用它提效；
4. 设备有 root（KernelSU），但不能假设所有目标设备都有。

来源：对话记录（多轮）、本仓库已完成的 PoC（mock / root 驱动）、AOSP 源码核验、本机实测数据。

## 2. 目标与非目标（草案）

**目标**：产出一个"屏幕能力层"——把「看见（画面 + 控件树）」和「操控（手势/文本/按键）」封装成稳定接口，
供 Agent 或人工镜像使用；在 root 设备上做到近乎零配置，在非 root 设备上做到最少步骤。

**非目标（本版）**：

- 不做公网远程控制（仅本机回环）；
- 不做 iOS / 桌面端；
- 不做游戏内存注入、不做绕过应用风控；
- 不重做 UI 框架（沿用现有 `gkd-vision` 的镜像界面）。

## 3. 用户与场景

| 角色 | 场景 | 关键诉求 |
| --- | --- | --- |
| Agent（本机自动化） | 看屏 → 决策 → 点击 → 再看 | 接口稳定、延迟低、可编程 |
| 人工（开发者/测试） | 在电脑浏览器里镜像手机并操作 | 画面流畅、点哪打哪 |
| 目标 App/服务 | 内置"看/控"能力给自己的用户 | 配置最少、权限可控 |

## 4. 调研与 PoC 结论（附证据）

| # | 结论 | 证据 |
| --- | --- | --- |
| 1 | GKD 的 HTTP 协议已具备「眼 + 手」：`captureSnapshot/getScreenshot/execSelector` 等 8 个端点 | `gkd-kit/gkd` 的 `InspectionServer.kt`、`ManualAction.kt`、`ActionPerformer.kt` |
| 2 | root 驱动可跑通：`screenrecord+ffmpeg` 约 **9.5fps**，`input tap` **52ms** | 本机实测（README「本机实测」） |
| 3 | `uiautomator dump` 在本机不可用，失败点是 `waitForIdle` 而非权限 | AOSP `DumpCommand.java` + 本机 3/3 复现 |
| 4 | root 可获取 `UiAutomation`（uid 0 被显式信任） | `UiAutomationConnection.java` + 本机 root 下 connect 成功 |
| 5 | root 本身不产生 a11y 树；`dumpsys activity top` 只能给 View 树（无 text、10s） | 本机实测 |
| 6 | 进程管理失误会触发 Android PhantomProcessKiller（108 个 ffmpeg 事故） | 系统日志 + [approach.md](approach.md) §9 |
| 7 | GKD 可直接作为开发期 oracle 与回退驱动 | 现有 `--driver gkd` 已可用 |

## 7. 关键技术风险

| ID | 风险 | 触发条件 | 早期信号 |
| --- | --- | --- | --- |
| R-01 | ROM 杀无障碍服务 | 长时间后台/省电模式 | 心跳丢失、`enabled_accessibility_services` 被改 |
| R-02 | 构建链路不可用 | 无 Android SDK / CI 配额 | CI 首次出包失败 |
| R-03 | 树质量不足 | 目标 App 用 WebView/Compose/自绘 | 快照节点数异常少、无 text |
| R-04 | 协议漂移 | GKD 版本升级（旧 `isClickable` / 新 `clickable`） | 归一化断言失败 |
| R-05 | 进程/fd 泄漏 | 长跑、频繁截图 | 内存曲线、fd 数持续上涨 |
| R-06 | 隐私与合规 | 画面含输入法/通知内容 | 日志出现敏感文本 |

## 10. 决策记录（Q-01 ~ Q-03）

裁决依据 [开发规范](../../DEVELOPMENT-GUIDELINES.md)：三条总原则（**解耦 / 傻瓜 / 全面**），
冲突时按 `安全 > 傻瓜 > 全面 > 解耦` 排序。

| ID | 问题 | 结论 | 依据 |
| --- | --- | --- | --- |
| Q-01 | 是否假设目标设备全部可 root | **不假设**。以 a11y App 为主形态，root 只作为增强与自动配置手段 | 全面（覆盖两端）；傻瓜（root 设备仍可零配置） |
| Q-02 | 能否随目标服务分发 | **可以，且默认解耦分发**。核心打成 `driver-core`（AAR），独立 APK 与"随包/嵌入"两种形态共用同一份核心 | 解耦（核心不绑宿主）+ 傻瓜（单包场景仍一键） |
| Q-03 | 是否把 `A11yService` 并进目标 App | **默认不并**。需要单包时由目标 App 依赖 `core` 模块并自行声明 Service，而不是复制代码 | 解耦优先；嵌入是可选形态而非默认 |

**三条原则到架构约束的落地**：

- 解耦 → `core`（能力）/ `adapters`（驱动）/ `shells`（APK、嵌入）三件套；驱动接口最小化、可插拔（G-01/G-02/G-03）；
- 傻瓜 → root 一键 0 步、非 root ≤ 3 步、错误码带动作、驱动自动回退（G-10~G-14）；
- 全面 → a11y / root / gkd / mock 四种驱动，P0 功能都有降级路径（G-20）。
